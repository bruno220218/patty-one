## Hospedagem e banco (sem Lovable)

- App hospedado na Cloudflare Workers (plano grátis); build com `bun run build`
  (nitro, preset `cloudflare-module`), deploy com `bun run deploy`.
- Banco/autenticação: projeto Supabase próprio (`dvndroghanmriumjfgqf`, plano grátis).
- Mudanças de esquema: escreva um novo arquivo em `drizzle/migrations/` e rode o SQL
  no SQL Editor do Supabase; depois regenere `src/integrations/supabase/types.ts`.
- Segredos (`SUPABASE_SERVICE_ROLE_KEY`, `AI_API_KEY`) ficam só no painel da
  Cloudflare, nunca no repositório. URL e chave publishable são públicas e ficam no `.env`.
- Mapa da Mídia OOH: chave de navegador do Google Maps em `VITE_GOOGLE_MAPS_KEY` (lida no
  build; restrinja a chave ao domínio do site no Google Cloud). Sem ela o mapa mostra um aviso
  e o resto da tela funciona.

## Project rules

- Persistence goes through repository interfaces in `src/lib/data/repositories.ts`, implemented on Supabase (`cloud-*.ts`) and exported from `src/lib/data/index.ts`; UI never queries the database directly — why: storage stays swappable without UI changes.
- Security-relevant task rules (copying checklist tasks, fixed-params lock, who/when completed, gestor-only uncheck) are enforced in the database (RPCs `create_project`/`duplicate_project`, trigger `guard_project_tasks`, column grants), checked by `tests/db/task-rules.check.sql`; pure display rules live in `src/lib/data/rules.ts` with `data-rules.test.ts` — why: the UI can't be trusted to enforce permissions.
- Roles live in `user_roles`: any role (`membro`/`gestor`) means an approved team member (`is_team_member`), which every project/task/blocker/profile policy requires; new sign-ups get no role until a gestor approves them in Equipe; gestor-only pages sit under `src/routes/_authenticated/_gestor/` — why: sign-up is open, so an account alone must not unlock team data, and roles must never come from client state.
- Removing a team member deletes their account via the gestor-checked server function `src/lib/data/team.functions.ts` (admin client loaded inside the handler); task completions and blockers keep a name snapshot (`completed_by_name`/`created_by_name`, set by DB triggers) — why: history of who did what must survive removal.
- UI reads data with TanStack Query hooks from `src/hooks/use-data.ts` (client-side only, no route loaders) and mutates through `useDataAction` — why: the session lives in the browser and signed-in routes render client-side.
- AI next-step suggestions stream from the server route `src/routes/api/next-steps.ts` → `src/lib/ai/next-steps.server.ts` (provedor compatível com OpenAI, opcional via `AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`); the route verifies the caller's bearer token and the browser sends a project snapshot — why: keeps the key and prompt on the server and AI use limited to signed-in people.
- Briefings (comercial → criação/projetos especiais) and visitas técnicas (comercial → PCP agenda → montagem realiza) follow the liberação pattern: flow rules in DB guard triggers (`guard_briefings`, `guard_visitas`), notices via `avisar()` into `notifications` (`link` column opens the page) — why: permissions can't depend on the UI.
- Attachments (`anexos`) store only Google Drive links: the browser uploads straight to Drive through the Apps Script web app with a short-lived HMAC ticket from `prepararUploadDrive` (`APPS_SCRIPT_URL`/`APPS_SCRIPT_SECRET`); nothing is stored in Supabase Storage — why: the free Supabase tier has only 1 GB for files.
- Painéis RGB (`/paineis`): everyone on the team sees the panels; only criação and gestão change vinhetas (RLS + `guard_painel_vinhetas`); every insert/update/retirada is written to `painel_historico` by a trigger with who and when; vinhetas are never deleted, only retired. Due-date notices come from `gerar_avisos_paineis()` (pg_cron daily, and the app calls it on load), once per stage and end date, to the representative matched by name or to gestão; checked by `tests/db/paineis.check.sql` — why: the history and the notices can't depend on the UI. The old Apps Script e-mails keep running from the spreadsheet.
- CI de vinheta (menu "CI", `/cis`): comercial/gestão create them through `salvar_ci` (numbering restarts each month: "10/Nov"), marking panels; each marked panel waits in `ci_paineis` until criação/gestão run `aprovar_ci_painel` (renews the same client's vinheta in place, else takes the lowest free slot) or `recusar_ci_painel`; all writes go through these security-definer functions, notices via `avisar()`; the vinheta file is an `anexos` row (`entidade = 'ci'`), uploaded to Drive like other attachments (picked in the new-CI form, sent right after `salvar_ci` returns the id); checked by `tests/db/ci.check.sql` — why: the slot choice and who may approve can't depend on the UI.
- Security (audit 18/11/2026): the AI route only serves approved members within a daily limit (`registrar_uso_ia`, 40/person/day); gestão sees account e-mails in Equipe (`equipe_emails`) to avoid approving impostors; a gestor can't set another gestor's password or remove another gestor's account (`team.functions.ts`; the Equipe screen hides the button), nor take away another gestor's Gestão or access (trigger `proteger_gestor`, 0030: through the app a `gestor` row in `user_roles` is only deleted by that person; other functions stay editable; checked by `tests/db/gestor-protegido.check.sql`); every password a gestor sets is logged in `equipe_eventos` (0027, gestão-only reads, written only by the server before the change, checked by `tests/db/log-senha.check.sql`); anon has no access to the public schema (0025, `tests/db/acesso-anonimo.check.sql`); security headers are added in `src/server.ts`; the weekly backup is GPG-encrypted with `BACKUP_PASSPHRASE` because this repository is public (Actions artifacts are downloadable by anyone with a GitHub account); checked by `tests/db/seguranca.check.sql`.
- Foto da veiculação (CI): comercial/criação/gestão ask through `solicitar_foto_ci` (only after the vinheta entered a panel, one open request per CI); the `checking` function (Checking fotográfico) gets the notice, uploads photos as `anexos` with `entidade = 'ci_foto'` (Drive: the CI folder › "Fotos do checking") and closes with `concluir_foto_ci` (needs at least one photo); checked by `tests/db/ci-foto.check.sql`.

Etapa 1 (0032): a liberação liga-se ao pedido (`liberacoes.venda_id`, só `tipo = 'pedido'`, não Cancelado, uma por pedido — índice `liberacoes_venda_unica`) e ao cadastro (`cadastro_id`, sempre o do pedido quando há um). Sem pedido, a liberação nova exige `motivo_sem_pedido` (Garantia/Retrabalho/Interno/Urgência); as antigas, sem pedido e sem motivo, continuam editáveis. Regras no gatilho `guard_liberacoes_pedido` (PCP aprovando e liberação aprovada não mudam a ligação; gestão pode). O pedido mostra a liberação e o botão "Liberar para produção" (`/liberacoes/nova?pedido=<id>`, que preenche cliente, contato, endereço, vendedor e itens; modelo Mídia quando todos os itens são Mídia OOH, `modeloDoPedido`); no editor, o campo Pedido também liga um pedido depois (Urgência). Checked by `tests/db/liberacao-pedido.check.sql`.
- Fluxo de produção, etapa 2 (0033) — Solicitar prazo: on the pedido ("Prazo de entrega", `src/components/app/prazo-pedido.tsx`) comercial/gestão ask with `solicitar_prazo` (optional desired date + note; not on a Cancelado pedido; one open request per pedido), PCP/gestão answer with `responder_prazo` (date required, not in the past — the PCP always decides), whoever asked or gestão cancel with `cancelar_prazo`; after an answer a new request can be made. History in `pedido_prazos` (team reads, writes only through those security-definer functions). Notices `prazo_solicitado` (to PCP) and `prazo_definido` (to whoever asked), link to the pedido. PCP menu "Prazos a definir" (`/prazos`) lists open requests, oldest first. The liberação opened from the pedido takes the latest answered date as data de entrega (`ultimoPrazo`, in `comercial-rules.ts`). Data access in `cloud-prazos.ts`; checked by `tests/db/prazo.check.sql`.
- Fluxo de produção, etapa 4 (0036) — ordens automáticas: a liberação ligada a um pedido gera, pelo gatilho `liberacoes_ordens` (`gerar_ordens_liberacao`, security definer, because comercial has no `can_gerir_operacao`), one order per pedido item (`ordens_producao.liberacao_id` + `venda_item_id`, unique per item) in the new status `Aguardando liberação`, with the default steps of the type (Instalação when the liberação has an address and the item isn't Mídia OOH, else Impressão), `data_prevista` = `data_entrega`. Approving the liberação moves them to `Aguardando`; changing its pedido redoes the waiting ones; deleting it deletes the waiting ones. While waiting, nobody starts or ticks steps (`guard_ordem_liberada` on apontamentos/etapas) and they stay out of planning (`ORDENS_FORA_DO_PLANEJAMENTO`). `Aguardando liberação` is never chosen by hand. A liberação with a pedido is approved without a Projeto (`AprovarComOrdensDialog`, `src/components/app/liberacao-ordens.tsx`); old ones keep the Projeto path. Manual order without pedido requires `motivo_sem_pedido` (Garantia/Retrabalho/Interno/Urgência; on insert or when the pedido is removed — old orders without one stay editable); an order from a liberação keeps its pedido. Checked by `tests/db/ordens-liberacao.check.sql`.
- Fluxo de produção, etapa 5 (0038) — mudança depois da liberação: the pedido stays editable. `salvar_venda` takes `foto_pedido()` before saving a pedido that has a liberação and calls `registrar_alteracao_pedido` (security definer, `can_vender`) after: what matters to production (status, cliente, vendedor, observação; per item descrição/categoria/ponto/período/quantidade — not prices) becomes one `liberacao_eventos` row of type `alteracao_pedido` (shown in the liberação history) and a `liberacao_pedido_alterado` notification to PCP/direção. A new item gets an order (`gerar_ordens_liberacao`); a removed item cancels its order if it hasn't started (no apontamento, no step done, still Aguardando/Aguardando liberação), otherwise the order continues and the comment says so; a changed item adds an event to its order. Checked by `tests/db/mudanca-pedido.check.sql`.
- Tempo das etapas (0035, adaptativo — feeds the PCP skill and the etapa 9 AI): on an order's step, Produção/Montagem/PCP/Gestão tap Iniciar (choosing who works; default the order's team), Pausar (reason required) and the checkbox is the baixa (concluding closes the open stretch). Each stretch is a row in `ordens_producao_apontamentos` (+ `ordens_producao_apontamento_colaboradores`), written only by `iniciar_etapa_producao` / `pausar_etapa_producao` / `atualizar_etapa_producao` (security definer, `can_executar_operacao`); one open stretch per step; starting a step moves an Aguardando order to Em andamento; changing the steps or cancelling the order closes open stretches as pauses. Person-hours = Σ(fim − início) × pessoas. PCP marks `ordens_producao.complexidade` (Simples/Média/Complexa). `amostras_tempo_etapas()` (security invoker) returns finished timed steps; the estimate is computed in `producao-rules.ts` (`estimarHorasEtapa`: median of the latest 20 samples of the most specific group with ≥3 — same service + step + complexity → step + complexity → service + step → step; stretches > 12 h are ignored), shown per step with the progress (held at 95% until the baixa). UI in `src/components/app/etapas-tempo.tsx`; tested in `tempo-etapas.test.ts`; checked by `tests/db/tempo-etapas.check.sql`.
- Dados para a skill PCP (button on `/producao`, Gestão and PCP; `src/components/app/skill-pcp-dialog.tsx`): builds the JSON the claude.ai PCP skill reads — `carteira_ordens` (open orders, nearest deadline first, each step with sector deduced from its name, situação, progresso, horas estimadas/gastas/restantes, material_ok = not paused for missing material, clima_dependente = installation/external/posting), `apontamentos_hoje` (one row per OS + step + person with the hours inside the day in Brasília, progress before/after and pause reasons) and `equipe_disponivel` (active colaboradores; sector and hours from their planning teams, 8 h without one; especialidades = the steps they worked most in 180 days, from `horas_colaborador_etapa`, 0035; `ausente` isn't recorded yet), plus `premissas` explaining each inference. Pure builder in `src/lib/data/skill-pcp.ts` (tested in `skill-pcp.test.ts`); loading in `operacaoRepository.entradaSkillPcp`. Copy or download; nothing is sent to an AI by the app.
- Fluxo de produção, etapa 6 (0039) — Etapas da ordem a partir do checklist: an order keeps the checklist its steps came from (`ordens_producao.checklist_id`) and, when that checklist has "Parâmetros fixos", `etapas_fixas` locks the steps (no insert/delete/rename/reorder; trigger `guard_ordens_etapas`, the same rule as `guard_project_tasks`; finishing steps still works). The database copies the checklist's tasks (`aplicar_etapas_ordem`, like `create_project`), so the app never sends step names with a checklist. Default checklist per order type in `ordens_checklist_padrao` (Gestão/PCP set it on `/checklists` through `definir_checklist_padrao`; component `checklist-padrao-ordens.tsx`); orders born from a liberação (`gerar_ordens_liberacao`, same signature as 0036 — 0038 calls it) use it, else the type's default steps. The PCP swaps an order's checklist with `trocar_checklist_ordem` only before it starts (no step done, no time recorded): in the approval dialog (one select per order, `liberacao-ordens.tsx`) or on the order page; with a checklist, changing the service no longer rebuilds the steps. Only gestão reopens a finished step (`atualizar_etapa_producao`). Checked by `tests/db/etapas-checklist.check.sql`.
