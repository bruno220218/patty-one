## Hospedagem e banco (sem Lovable)

- App hospedado na Cloudflare Workers (plano grátis); build com `bun run build`
  (nitro, preset `cloudflare-module`), deploy com `bun run deploy`.
- Banco/autenticação: projeto Supabase próprio (`dvndroghanmriumjfgqf`, plano grátis).
- Mudanças de esquema: escreva um novo arquivo em `drizzle/migrations/` e rode o SQL
  no SQL Editor do Supabase; depois regenere `src/integrations/supabase/types.ts`.
- Segredos (`SUPABASE_SERVICE_ROLE_KEY`, `AI_API_KEY`) ficam só no painel da
  Cloudflare, nunca no repositório. URL e chave publishable são públicas e ficam no `.env`.
- Mapa da Mídia OOH: chave de navegador do Google Maps em `VITE_GOOGLE_MAPS_KEY` (lida no
  build; restrinja a chave ao domínio do site no Google Cloud). Sem ela o mapa mostra um aviso
  e o resto da tela funciona.

## Project rules

- Persistence goes through repository interfaces in `src/lib/data/repositories.ts`, implemented on Supabase (`cloud-*.ts`) and exported from `src/lib/data/index.ts`; UI never queries the database directly — why: storage stays swappable without UI changes.
- Security-relevant task rules (copying checklist tasks, fixed-params lock, who/when completed, gestor-only uncheck) are enforced in the database (RPCs `create_project`/`duplicate_project`, trigger `guard_project_tasks`, column grants), checked by `tests/db/task-rules.check.sql`; pure display rules live in `src/lib/data/rules.ts` with `data-rules.test.ts` — why: the UI can't be trusted to enforce permissions.
- Roles live in `user_roles`: any role (`membro`/`gestor`) means an approved team member (`is_team_member`), which every project/task/blocker/profile policy requires; new sign-ups get no role until a gestor approves them in Equipe; gestor-only pages sit under `src/routes/_authenticated/_gestor/` — why: sign-up is open, so an account alone must not unlock team data, and roles must never come from client state.
- Removing a team member deletes their account via the gestor-checked server function `src/lib/data/team.functions.ts` (admin client loaded inside the handler); task completions and blockers keep a name snapshot (`completed_by_name`/`created_by_name`, set by DB triggers) — why: history of who did what must survive removal.
- UI reads data with TanStack Query hooks from `src/hooks/use-data.ts` (client-side only, no route loaders) and mutates through `useDataAction` — why: the session lives in the browser and signed-in routes render client-side.
- AI next-step suggestions stream from the server route `src/routes/api/next-steps.ts` → `src/lib/ai/next-steps.server.ts` (provedor compatível com OpenAI, opcional via `AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`); the route verifies the caller's bearer token and the browser sends a project snapshot — why: keeps the key and prompt on the server and AI use limited to signed-in people.
- Briefings (comercial → criação/projetos especiais) and visitas técnicas (comercial → PCP agenda → montagem realiza) follow the liberação pattern: flow rules in DB guard triggers (`guard_briefings`, `guard_visitas`), notices via `avisar()` into `notifications` (`link` column opens the page) — why: permissions can't depend on the UI.
- Attachments (`anexos`) store only Google Drive links: the browser uploads straight to Drive through the Apps Script web app with a short-lived HMAC ticket from `prepararUploadDrive` (`APPS_SCRIPT_URL`/`APPS_SCRIPT_SECRET`); nothing is stored in Supabase Storage — why: the free Supabase tier has only 1 GB for files.
- Painéis RGB (`/paineis`): everyone on the team sees the panels; only criação and gestão change vinhetas (RLS + `guard_painel_vinhetas`); every insert/update/retirada is written to `painel_historico` by a trigger with who and when; vinhetas are never deleted, only retired. Due-date notices come from `gerar_avisos_paineis()` (pg_cron daily, and the app calls it on load), once per stage and end date, to the representative matched by name or to gestão; checked by `tests/db/paineis.check.sql` — why: the history and the notices can't depend on the UI. The old Apps Script e-mails keep running from the spreadsheet.
- CI de vinheta (menu "CI", `/cis`): comercial/gestão create them through `salvar_ci` (numbering restarts each month: "10/Nov"), marking panels; each marked panel waits in `ci_paineis` until criação/gestão run `aprovar_ci_painel` (renews the same client's vinheta in place, else takes the lowest free slot) or `recusar_ci_painel`; all writes go through these security-definer functions, notices via `avisar()`; the vinheta file is an `anexos` row (`entidade = 'ci'`), uploaded to Drive like other attachments (picked in the new-CI form, sent right after `salvar_ci` returns the id); checked by `tests/db/ci.check.sql` — why: the slot choice and who may approve can't depend on the UI.
- Security (audit 18/11/2026): the AI route only serves approved members within a daily limit (`registrar_uso_ia`, 40/person/day); gestão sees account e-mails in Equipe (`equipe_emails`) to avoid approving impostors; a gestor can't set another gestor's password or remove another gestor's account (`team.functions.ts`; the Equipe screen hides the button), nor take away another gestor's Gestão or access (trigger `proteger_gestor`, 0030: through the app a `gestor` row in `user_roles` is only deleted by that person; other functions stay editable; checked by `tests/db/gestor-protegido.check.sql`); every password a gestor sets is logged in `equipe_eventos` (0027, gestão-only reads, written only by the server before the change, checked by `tests/db/log-senha.check.sql`); anon has no access to the public schema (0025, `tests/db/acesso-anonimo.check.sql`); security headers are added in `src/server.ts`; the weekly backup is GPG-encrypted with `BACKUP_PASSPHRASE` because this repository is public (Actions artifacts are downloadable by anyone with a GitHub account); checked by `tests/db/seguranca.check.sql`.
- Foto da veiculação (CI): comercial/criação/gestão ask through `solicitar_foto_ci` (only after the vinheta entered a panel, one open request per CI); the `checking` function (Checking fotográfico) gets the notice, uploads photos as `anexos` with `entidade = 'ci_foto'` (Drive: the CI folder › "Fotos do checking") and closes with `concluir_foto_ci` (needs at least one photo); checked by `tests/db/ci-foto.check.sql`.
- Cadastros (`/cadastros`, vindos do sistema PattyOne/SIGE): the whole approved team reads; comercial and gestão write (`can_editar_cadastros`); only gestão deletes and imports (`/importar`, CSV parsed by the dependency-free `src/lib/data/csv.ts`); bank details (`cadastros_bancario`) are direção/financeiro only (`can_ver_bancario`, new função `financeiro`). Saves go through `salvar_cadastro` (security invoker, so RLS applies), the list through `listar_cadastros` (50 per page, filters in the URL); SIGE restriction flags (`restricao_sige`, `restricao_observacao`, `dados_sige`) are import-owned and never sent by the form. Field lists, masks and spreadsheet conversions live in `src/lib/data/cadastros-rules.ts` (tested); checked by `tests/db/cadastros.check.sql` — why: who may see bank data can't depend on the UI.
- Configurações (`/configuracoes`): aparência (claro/escuro/automático — automático clears `pattyone:theme` so `THEME_INIT_SCRIPT` follows the system), perfil (own `display_name` via `teamRepository.updateMyName`) and sair; also linked from the account menu.
- Migração do PattyOne: the old system's modules are being brought here in the order Cadastros → operação (Produção, Planejamento, Equipes de planejamento, Veículos, Catálogos, Programação) → Comercial → Mídia OOH → Financeiro, always on this repository's patterns (folder routes, `cloud-*.ts` repositories, `can_*` functions, files on Drive via `anexos`); see `roadmap.md`.
- Operação (setor Produção, vinda do PattyOne): ordens de produção (`/producao`, steps + history with a name snapshot, deadline alerts), cronograma (`/planejamento`, conflicts and urgency reservations checked in `salvar_planejamento`), Programação Produção (`/planejamento/programacao`, batch save via `salvar_programacao_lote`, same-day shared person/vehicle is only an amber warning confirmed into `conflito_confirmado`), equipes de planejamento, veículos and produtos/serviços/colaboradores. Everyone approved reads; Gestão and PCP write (`can_gerir_operacao`); Produção and Montagem also tick order steps (`atualizar_etapa_producao`) and change a service's situation (`atualizar_status_programacao`) (`can_executar_operacao`). Used catalog items, vehicles and colaboradores are deactivated instead of deleted. Images of services/appointments are `anexos` (`entidade` `programacao`/`agendamento`) on Drive, and their links go into the WhatsApp text. `venda_id` points to the pedido (`vendas`, foreign key since 0020; deleting the pedido leaves the order without one); `ponto_id` points to the mídia point (`pontos_midia`, foreign key since 0022). Data access is `src/lib/data/cloud-operacao.ts` (each table read separately and joined in code); pure rules in `producao-rules.ts`, `planejamento-rules.ts`, `programacao-rules.ts` (tested in `operacao-rules.test.ts`); checked by `tests/db/operacao.check.sql`.
- Comercial (vindo do PattyOne): propostas and pedidos (`/comercial`, `/comercial/$vendaId` — `nova-proposta`/`novo-pedido` open an empty one) of the group companies (`empresas`), items Mídia OOH/Produção/Serviço/Item livre, PDF (`src/lib/venda-pdf.ts`), proposta → pedido once via `converter_proposta` (the proposta becomes Aprovada; never from a Recusada one); a pedido lists its ordens de produção and opens a new one already linked (`/producao/nova?pedido=<id>`). Everyone approved reads; comercial and gestão write (`can_vender`, saves through `salvar_venda`, security invoker so RLS applies, header + items replaced in one call, the type never changes); only gestão deletes. Histórico comercial do SIGE (`/comercial/historico`, read-only) is imported by gestão at `/importar-historico` (several CSVs at once, contracts and reservations merged by authorization in `prepararHistoricoSige`, linked to a cadastro/empresa only when exactly one name matches). Totals, situations and the SIGE reader live in `src/lib/data/comercial-rules.ts` (tested); data access in `cloud-comercial.ts`; checked by `tests/db/comercial.check.sql`.
- Menu por setor (`src/components/app/app-shell.tsx`, `SETORES`): Comercial, Produção, Criação, Projetos Especiais, PCP (also direção, montagem and produção), Checking (`soParaFuncao`: only people with that function, gestão has the item in Comercial), Financeiro (financeiro and direção) and Gestão (gestão sees every sector); an item without `to` shows "em breve"; the same page can sit in several sectors and lights up in all of them (`chaveItem`). Briefings are split by area through `?destino=`: "Briefing Criação" and "Briefing Orçamento" (= Projetos Especiais) each list and create only their own kind; the form has no area picker.
- Comentários nas liberações: any approved member comments through `comentar_liberacao` (event `comentario` in `liberacao_eventos`, which takes no direct writes); it notifies who created the liberação, PCP/direção and earlier commenters (`liberacao_comentario`). Mídias dos painéis (`/paineis/midias`): `paineis.midias_link` (Drive folder for RGB 1–7, vnnox for PA01), changed only through `salvar_link_midias_painel` (criação/gestão). Checklists: gestão and PCP manage them and start projects from them (`can_gerir_checklists`, route guard in `checklists.*.tsx`). Medidas (`/medidas`) is a read-only view of the visitas técnicas (measures + vistoria), edited in Visitas técnicas. Checked by `tests/db/comentarios-midias-checklist.check.sql`.
- Mídia OOH (vinda do PattyOne; menu Produção › "Mapeamento das áreas" = `/midia-ooh` and "Datas de colagens" = `/midia-ooh/bissemanas`, also under Comercial › Vendas): points with type, location on a Google map (`src/components/app/mapa-pontos.tsx`, key in `VITE_GOOGLE_MAPS_KEY`), measures and photos as `anexos` (`entidade = ponto_midia`, Drive › "Mídia OOH" › point folder). Everyone approved reads; Gestão, Comercial and PCP edit points (`can_editar_midia`; the SIGE columns `id_sige`/`codigo_sige`/`dados_sige` are outside the column grant); only gestão deletes points and manages types (a type in use is deactivated) and the calendar. The official SIGE bi-week calendar is generated by `gerar_calendario_bissemanas` (continuous 14-day cycles anchored on 2025-12-29, each cycle belongs to the ISO year of its last day — fixed in 0023 against the PattyOne export, SIGE code = 2 × number; 2019–2030 seeded). Occupancy (no row = Livre) changes only through `marcar_ocupacao` (Gestão and Comercial, `can_marcar_ocupacao`; checks the calendar; keeps who changed it with a name snapshot). Pure rules in `src/lib/data/midia-rules.ts` (tested); data access in `cloud-midia.ts`; checked by `tests/db/midia.check.sql`.
- Checkout fotográfico (fim da veiculação da CI, menu "Checkout Fotográfico" = `/cis?aba=checkout`): same flow as the checking photo, in the same table `ci_fotos_pedidos` with `etapa = 'checkout'` (one open request per CI and step); comercial/criação/gestão ask through `solicitar_checkout_ci` (only after the vinheta entered a panel), the `checking` function gets the notice, uploads photos as `anexos` with `entidade = 'ci_checkout'` (Drive: the CI folder › "Fotos do checkout") and closes with `concluir_foto_ci` (counts only that step's photos); checked by `tests/db/ci-checkout.check.sql`.
- Financeiro (vindo do PattyOne; menu Financeiro, `/financeiro?aba=receber|pagar|comissoes|aluguel|energia`): contas a receber (optional cliente, pedido and empresa; Receber/Cancelar/Reabrir — the `recebido_em` date is kept by a trigger, set only while Recebido), contratos de aluguel dos pontos (`midias` holds the point codes as in the SIGE, linked on screen to `/midia-ooh`; monthly cost by periodicity) and contratos de energia. Only Gestão, Direção and Financeiro read and write (`can_financeiro`); only Gestão and Direção delete (`can_excluir_financeiro`). Contas a pagar (0029, new — not in the PattyOne): categories Fornecedor/Aluguel/Energia/Comissão/Imposto/Outros, paid to a cadastro or a free-text name; `gerar_parcelas_aluguel(até)` creates rent installments from active recurring contracts (max 24 each, unique per contract + due date) and moves the contract's next due date. Comissões are payables created by the trigger `gerar_comissoes_recebimento` when a conta a receber linked to a pedido becomes Recebido ("quando o cliente paga"): the pedido's vendedor at the percentage in `comissao_vendedores`, plus the agency/representative commission from the client's cadastro; undoing the receipt removes the unpaid ones. Also checked by `tests/db/contas-pagar.check.sql`. Pure rules in `src/lib/data/financeiro-rules.ts` (tested); data access in `cloud-financeiro.ts`; checked by `tests/db/financeiro.check.sql`.
